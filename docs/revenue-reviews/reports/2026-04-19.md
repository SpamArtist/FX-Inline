## 5. Marketplace and review intelligence

### Positive themes

- Users love inline conversion because it preserves browsing flow.
- Hover, highlight, and right-click conversion are repeatedly praised.
- Privacy-light behavior still matters. “No account,” “local settings,” and “no tracking” are still strong selling points.
- Hybrid auto plus manual control is valued.
- Merchant-side reviewers reward onboarding help and fast support.

### Negative themes

- Setup complexity gets punished immediately.
- Wrong values or stale rates kill trust fast.
- Runtime overhead on dynamic pages creates strong negative reviews.
- Save-state bugs and confusing settings surfaces are common complaint magnets.
- Bad defaults and unreadable highlight/display choices get called out even when the conversion engine works.
- Mobile gaps matter on commerce products.

### Feature requests recurring across the category

- Tax or fee handling
- More currencies and locale formats
- Better highlight and display controls
- Allowlist or blocklist controls
- Faster preferred-currency setup
- Multi-currency view
- Better search, ordering, and persistence in settings

### Trust concerns

- Users notice broad permissions.
- Users notice PII disclosures.
- Users notice exposed API keys.
- Zero-review products start from a trust hole.
- FX Inline still has almost no public proof of trust: no review corpus, no case studies, no testimonials, and inconsistent public versioning.

### Revenue-relevant insights from review mining

- Simplicity is a conversion feature.
- Accuracy is a trust feature.
- Performance is a rating feature.
- Support is a monetization feature for B2B localization products.
- Hard consumer paywalls are risky in this category unless trust and traction already exist.

## 13. Detailed execution playbook for the single recommended focus

### Phase 1: Preparation

1. Choose the exact wedge.
   - Use: USD-only SaaS pricing pages with international traffic.
   - Do not start with Shopify merchants. That market already has mature paid localization apps and stronger incumbents.
   - Do not start with general consumer installs. That is slower and noisier.

2. Define the pilot scope in one paragraph.
   - Promise: show local-currency hints beside existing public plan prices on the prospect’s pricing page.
   - Keep in scope: public pricing page only, local-currency hints, clear display rules, lightweight implementation, proof of improved comprehension.
   - Keep out of scope: checkout localization, tax/VAT correctness guarantees, subscription billing, exchange-rate history, account systems, full e-commerce localization.

3. Write the offer in buyer language.
   - Use language like: “Add local-currency price hints to your public pricing page in days.”
   - Do not lead with “browser extension.”
   - Do not lead with “currency parsing.”
   - Do not lead with “AI.”

4. Prepare a prospect-scoping checklist.
   - Ask for: pricing-page URL, source currency, target countries, preferred display style, whether taxes are already included, and any styling constraints.
   - Save this as the first sales asset, not as code.

### Phase 2: Website conversion

5. Rewrite the website home page.
   - Inspect and change: `apps/website/index.html`, `apps/website/styles.css`, `apps/website/main.js`.
   - Replace the generic hero with a pilot-oriented hero.
   - Replace the current section-ordering so the first actions are “Request pilot” and “See a real example.”
   - Remove the “update these links once published” note completely.
   - Add a section called “Who this is for” with SaaS pricing pages as the first example.

6. Add proof blocks.
   - Add 2-3 before/after screenshots showing price cards before and after local-currency hints.
   - Add a short trust block:
     - settings stored locally in the current extension,
     - rates fetched from public FX providers,
     - current tech runs client-side,
     - pilot implementation is intentionally narrow.
   - Add a limitations block so the offer looks honest instead of inflated.

7. Add a real CTA path.
   - In `apps/website/index.html`, add a visible pilot-request CTA.
   - In `apps/website/main.js`, wire the CTA to a simple contact path or booking path and add click tracking.

### Phase 3: Proof asset production

8. Produce personalized demos with the current extension.
   - Use the extension on public target pages to show the effect visually.

   - Use AI design tools to annotate screenshots quickly with callouts like “same page, local currency visible.”

9. Create three reusable demo categories.
   - One SaaS pricing page.
   - One travel or booking page.
   - One marketplace or shopping page.
   - Use those on the site and in outreach until personalized proof exists.

10. Build the first prospect list.
   - Target 30 companies whose public pricing pages still show a single foreign currency.
   - Prefer companies with self-serve pricing and obvious international traffic.
   - Avoid companies that already show localized pricing.

### Phase 4: Outbound and qualification

11. Write one short outbound email and one shorter follow-up.
   - Email 1: show the problem on their own page and link to the proof asset.
   - Follow-up: restate the fixed-fee pilot and the narrow scope.
   - Do not send long feature lists.
   - Do not market the parser.

   - If they worry about trust: explain the narrow scope and current privacy boundaries.
   - If they worry about styling: show that the pilot only needs lightweight secondary price hints.
   - If they worry about full localization: say the pilot is not a full localization platform.
   - If they worry about runtime cost: offer a narrow allowlisted implementation for one page.

13. Qualify hard.
   - Continue only if the prospect owns a public pricing page, has international buyers, and values faster price comprehension.
   - Walk away if they want full checkout localization or full tax correctness from day one.

15. Include review-driven improvements only where they help the pilot.
   - Add a readable display treatment.

16. Validate on the actual target page.
   - Test desktop and mobile.
   - Test dynamic plan toggles.
   - Test ambiguous currency symbols.
   - Test if the secondary price remains readable on both light and dark surfaces.
   - Existing repo tests prove the general engine, not the client page.

### Phase 6: Measurement and iteration

17. Measure the sales process, not vanity metrics.
   - Track: outbound sent, reply rate, calls booked, pilot sold, days to close.
   - After launch, track: client satisfaction, request to expand, and willingness to provide a testimonial.
   - A single paid pilot matters more than install vanity metrics right now.

18. Turn the first pilot into reusable proof.
   - Ask for one quote.
   - Ask for permission to anonymize or name the case study.
   - Add the result back onto the website immediately.

19. Decide the next path only after the first pilot.
   - If buyers want custom work: stay services-first.
   - If buyers want a reusable integration component: package parser/runtime pieces and sell support/licensing.
   - If consumer traction unexpectedly grows: revisit marketplace optimization later.

20. Know the stop condition.
   - If 30 targeted outbound contacts produce no serious interest, stop forcing the B2B pilot thesis.
   - The fallback is package-led services or content-led affiliate testing, not more website polish.
