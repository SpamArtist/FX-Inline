The core reading rule

Async code looks sequential, but it is really “start work, wait, continue.” The mistake beginners make is reading it as if everything happens immediately and synchronously.

In this repository, async code usually appears for four reasons:

  • talking to browser APIs such as alarms, tabs, or storage
  • loading cached state or fetching fresh data
  • lazily importing modules only when needed
  • recovering from failure with cached or null-safe fallback values

Example 1: startup work in the background script

In apps/extension/entrypoints/background.ts, look at this helper: 

async function initializeRateRefresh(forceRefresh = false) {
  await Promise.all([
    scheduleRateRefreshAlarm(),
    getRates({ forceRefresh }),
  ]);
}

Read this line by line:

  1. The function is async, so callers receive a promise.
  2. Promise.all([...]) starts both tasks right away.
  3. The function waits until both are finished or until one rejects.
  4. If either task fails, the whole await throws.

Key reading question: “are these tasks independent enough to run in parallel?” Here the answer is yes, because scheduling an alarm and fetching rates do not need to happen one after the other.

Example 2: fire-and-observe event handlers

Still in background.ts, notice this call site: 

browser.runtime.onStartup.addListener(() => {
  void initializeRateRefresh().catch((error) => {
    logRateRefreshError("onStartup", error);
  });
});

This is not the same as await initializeRateRefresh(). The event listener starts the work and returns immediately. The void says “ignore the promise value here,” while .catch(...) still handles failures explicitly.

Reading rule: in event-driven extension code, this pattern often means “kick off background work, but do not block the event callback on the result.”

Example 3: fallback logic in rates loading

In apps/extension/utils/rates/index.ts: 

const cached = await getCachedRateSnapshot();

if (
  !opts?.forceRefresh &&
  isValidSnapshot(cached) &&
  shouldUseMarketDayCache(cached.marketDayKey)
) {
  return cached;
}

try {
  const fetched = await fetchLatestUsdSnapshotFromClient();
  await setCachedRateSnapshot(snapshotWithMarketDay);
  return snapshotWithMarketDay;
} catch (error) {
  if (isValidSnapshot(cached)) {
    return cached;
  }
  throw error;
}

This is the canonical repo pattern for resilient async flow:

  • read cached state first
  • return early if cache is good enough
  • otherwise fetch fresh data
  • if fetch fails, fall back to cached data when possible
  • only throw if there is no safe cached fallback

When reading a try/catch block here, ask: “what failure is this code trying to survive?”

Example 4: lazy module loading in hydration

In apps/extension/hooks/useCurrencyReducer.hydration.ts: 

if (!readUserSettings || !readRates) {
  const [{ getUserSettings }, { getCachedRateSnapshot }] = await Promise.all([
    import("../utils/appStorage"),
    import("../utils/rates/cache"),
  ]);
  readUserSettings = readUserSettings ?? getUserSettings;
  readRates = readRates ?? getCachedRateSnapshot;
}

There are two important JavaScript ideas here:

  • import(...) is dynamic import. It loads a module at runtime instead of at file parse time.
  • The array destructuring on the left unpacks the resolved modules in order.

Read this as: “if dependencies were not injected, load both modules in parallel, then take the functions I need from each.”

Example 5: safe null fallback for UI hydration

The same hydration file ends with: 

try {
  const settings = await readUserSettings();
  const rateSnapshot = await readRates();

  return {
    preferredCurrency: getPrimaryTargetCurrency(settings.scopes.allUrls),
    rateSnapshot,
  };
} catch {
  return {
    preferredCurrency: null,
    rateSnapshot: null,
  };
}

This is not just error handling. It defines a UI contract: if hydration fails, the reducer still receives a predictable object shape.
