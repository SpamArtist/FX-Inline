Lesson 0001

Read This Extension Without Guessing

This lesson teaches one skill only: how to open a JavaScript or TypeScript file in this repository and quickly answer, “what role does this file play, and what language features do I need to understand it?”

Mission fit

You want to understand this WXT extension well enough to navigate and modify it. That means your first win is not writing code. It is reading code with a reliable method.

The map of the repo

Start with directory roles, not syntax details. In this repository, JavaScript and TypeScript appear in a few distinct layers:

  • apps/extension/entrypoints/: where the browser extension starts running
  • apps/extension/utils/: shared business logic and storage helpers
  • apps/extension/hooks/: Preact state logic for UI behavior
  • packages/currency-detection/src/: plain JavaScript package for parsing currency text
  • packages/inline-runtime/src/: plain JavaScript runtime package used by the content logic
  • wxt.config.ts: build-time configuration, chunking rules, and extension bundling behavior

That split matters because the same language feature can mean different things in each layer. An async function in the background entrypoint usually coordinates browser APIs; an async function in storage code usually loads or sanitizes persisted state.

The five-question reading method

  1. What does this file import?
  2. What does this file export?
  3. Which functions are pure data transforms, and which touch browser/runtime state?
  4. Where are the async boundaries?
  5. Is this file an entrypoint, a helper, state logic, or a reusable package?

If you can answer those five questions, you can usually modify the file safely or at least know what to inspect next.

Example 1: background entrypoint

Look at apps/extension/entrypoints/background.ts. It is an entrypoint, so you should expect wiring code rather than deep business logic. 

import { getRates } from "@/utils/rates/index";
import { shouldOpenWelcomePage } from "@/utils/installLifecycle";
import { browser } from "wxt/browser";

export default defineBackground(() => {
  browser.runtime.onInstalled.addListener((details) => {
    void initializeRateRefresh(true).catch((error) => {
      logRateRefreshError("onInstalled", error);
    });
  });
});

What JavaScript matters here?

  • import: tells you this file depends on rate fetching, install logic, and WXT browser APIs.
  • export default: this file exposes one main thing, the background entrypoint definition.
  • () => { ... }: arrow functions are used heavily for event callbacks.
  • async helper functions above the export: setup work is factored into named functions instead of inlined.
  • void promise.catch(...): the code intentionally starts async work from an event listener without awaiting it there.

Repo-specific insight: entrypoint files often answer “when does this happen?” not “how does the full feature work?”

Example 2: content script entrypoint

Now look at apps/extension/entrypoints/content/index.tsx: 

export default defineContentScript({
  matches: ["<all_urls>"],
  cssInjectionMode: "manual",
  main(ctx) {
    createContentActivationController(ctx).start();
  },
});

The important JavaScript concept here is the object literal passed into defineContentScript. This object configures the content script and provides a main method. When you see this shape, read it as “WXT configuration plus startup code.”

Example 3: storage logic

In apps/extension/utils/appStorage.ts, the code becomes more data oriented. 

const VALID_CURRENCY_CODES = new Set(
  Object.values(CurrencyCode),
);

export async function getUserSettings() {
  const stored = await readLocalStorageValue(SETTINGS_KEY, DEFAULT_USER_SETTINGS);
  const sanitized = sanitizeUserSettings(stored);
  return sanitized;
}
  • const means a binding should not be reassigned.
  • new Set(...) creates a lookup structure for membership checks.
  • Object.values(...) turns an object-like enum into an array.
  • await marks a pause while storage is read.
  • Small helper functions such as asCurrencyCode encode validation rules.

This file is a good example of “JavaScript for shaping data.” When reading files like this, focus on inputs, outputs, and guards.

Example 4: UI state with hooks

In apps/extension/hooks/useCurrencyReducer.ts, you meet Preact hooks. Underneath the framework syntax, the JavaScript ideas are still familiar: variables, functions, arrays, async work, and closures. 

const [rateSnapshot, setRateSnapshot] = useState(null);

useEffect(() => {
  let canceled = false;

  const loadSettingsAndRates = async () => {
    const hydratedState = await loadCurrencyReducerHydration();
    if (canceled) return;
    setRateSnapshot(hydratedState.rateSnapshot);
  };

  loadSettingsAndRates();

  return () => {
    canceled = true;
  };
}, []);

Two JavaScript reading points matter here:

  • The inner async function closes over canceled. That is a closure.
  • The empty dependency array [] belongs to the hook API, but the body is still ordinary JavaScript logic.

Example 5: plain JavaScript packages

The packages under packages/ are especially good for learning because they are closer to plain JavaScript than the extension UI layer. 

import { createCurrencyParser } from "./parser-core.js";

const defaultParser = createCurrencyParser();

export function parseCurrencyValue(input, options) {
  return defaultParser.parseValue(input, options);
}

This is classic module design:

  • import one dependency
  • create one shared object
  • export a small surface area of named functions

If you ever feel lost in the extension layer, drop into one of these package files. They are often simpler and reveal the repo’s coding style more clearly.

Checkpoint

After this lesson, you do not need to know all of JavaScript. You only need to be able to open a file and recognize:

  • module boundaries via import and export
  • behavior grouped into functions
  • state represented as objects and arrays
  • delayed work marked by async and await
  • runtime starting points under WXT entrypoints

If anything in this lesson feels fuzzy, ask follow-up questions directly. A good next step would be a second lesson on “promises and async flow in this extension” or “how to read TypeScript syntax without being blocked by it.”
