Lesson 0003

Trace a Feature Through the Content Runtime

This lesson teaches one skill only: how to trace a single user-visible behavior across multiple modules and understand why the system is split the way it is. The behavior is simple to say but architecturally rich: a page contains price-like text, the extension detects that signal, promotes itself into a full content worker, and then maintains conversions as the page changes.

The feature path

Here is the execution path you are learning to follow:

  1. apps/extension/entrypoints/content/index.tsx starts the content script.
  2. contentActivation.ts decides whether the page is interesting enough to activate.
  3. When the page looks interesting, the extension dynamically imports content-worker.js.
  4. contentWorker.ts creates the steady-state runtime and the mutation batching machinery.
  5. conversionRuntime.ts hydrates settings and rates, configures the shared inline runtime, and reacts to later updates.
  6. The shared package @fx-inline/inline-runtime/extension does the actual conversion work.

This is the first important jump in level: you are no longer reading files in isolation. You are reading a pipeline.

Stage 1: lightweight activation instead of eager runtime startup

The content entrypoint is tiny: 

export default defineContentScript({
  matches: ["<all_urls>"],
  cssInjectionMode: "manual",
  main(ctx) {
    createContentActivationController(ctx).start();
  },
});

That tells you something architectural immediately: the extension does not begin by spinning up the full conversion runtime on every page. It begins with a cheap controller whose job is to decide whether full activation is justified.

Advanced reading question: why is this split valuable for an extension that runs on <all_urls>?

Stage 2: signal detection as a promotion gate

In contentActivation.ts, the controller performs cheap detection first. 

if (scanRootForCurrencyActivationSignal(body)) {
  void loadWorker().catch((error) => {
    console.warn("[fx-inline] Failed to start content worker after initial price scan", error);
  });
  return;
}

The controller is effectively asking: “do I have enough evidence that this page contains currency-like text?” Only then does it promote the page into the heavier runtime.

Notice the cost-control strategy:

  • regex-based signal scanning instead of full conversion work
  • text and node count limits to cap scan cost
  • a mutation observer plus debounce for late-arriving page content

Stage 3: lazy loading the worker

Promotion happens here: 

async function importContentWorker(options = {}) {
  setContentWorkerStartupOptions(options);
  await import(getExtensionResourceUrl("content-worker.js"));
}

This is not just syntax. It is a design move:

  • setContentWorkerStartupOptions(...) stores boot options in a global handoff slot.
  • import(...) loads the heavier worker only when needed.
  • getExtensionResourceUrl(...) resolves the extension-bundled script path at runtime.

The paired file contentWorkerStartup.ts exists purely to create this handoff seam. That is a good example of a small file with architectural weight.

Stage 4: worker startup defines the steady-state system

Once promoted, contentWorker.ts stops being about detection and starts being about long-lived coordination. 

const conversionRuntime = createContentConversionRuntime();
const mutationBatcher = createMutationRootBatcher({
  shouldIgnoreMutations: conversionRuntime.shouldIgnoreMutations,
  collectRoots: (mutations) => collectMutationConversionRoots(...),
  enqueueRoots: conversionRuntime.enqueueMutationRoots,
});

This is the next important reading heuristic: when you see a factory creating a runtime object and wiring adapters around it, you are looking at the composition root for that subsystem.

The worker owns three concerns:

  • lifecycle and cleanup
  • mutation observation and batching
  • UI affordances like the selection popup and event capture

Stage 5: the runtime object is really a local service

In conversionRuntime.ts, the returned object is: 

return {
  initialize,
  onSettingsStorageUpdate,
  enqueueMutationRoots,
  recordSelectionConversion,
  shouldIgnoreMutations,
  cleanup,
};

Treat this as a local service with hidden state:

  • settings, resolvedSettings, and rateSnapshot are private state.
  • initialize() performs hydration and startup.
  • onSettingsStorageUpdate(...) is an event handler for state changes.
  • cleanup() closes the lifecycle.

That means this file is closer to a state machine than to a bag of helpers.

Stage 6: mutation batching is the performance seam

Raw DOM mutation events would be too noisy to process directly. The batcher solves that: 

function push(mutations) {
  if (shouldIgnoreMutations()) return;

  pendingMutations.push(...mutations);
  if (pendingTimer !== null) return;

  pendingTimer = scheduleTimeout(flush, debounceMs);
}

That is an architectural seam, not just a utility. It decouples observation frequency from conversion frequency. In other words: “the DOM may change constantly, but the expensive conversion pass should happen on our schedule, not the browser’s raw event rate.”

Stage 7: package boundaries reveal intended abstractions

The app layer does not reach deep into implementation details. Instead it uses: 

import { createInlineRuntime } from "@fx-inline/inline-runtime/extension";

That is a strong signal that the package boundary is deliberate. The content runtime configures and feeds the shared runtime, but the package owns the conversion mechanics.

Advanced reading rule: when a package import sits at the center of a subsystem, ask what responsibilities stay in the app layer and what responsibilities are delegated.

Practice: explain the design, not just the code

  1. Why does the extension use contentActivation.ts before loading the worker?
  2. What problem does createMutationRootBatcher(...) solve that a raw MutationObserver callback would not?
  3. Why is createContentConversionRuntime() better modeled as a runtime service than as a set of stateless helpers?
  4. Why is the import from @fx-inline/inline-runtime/extension a meaningful architectural clue?

What you should be able to do now

  • trace one feature across multiple files without losing the thread
  • separate activation code from steady-state runtime code
  • spot performance seams such as batching and lazy loading
  • recognize when a factory-returned object is really a local service or state machine
  • use package boundaries to infer intended abstractions

If this lands cleanly, the next lesson should move again from “trace the pipeline” to “evaluate the design”: identifying where this architecture is resilient, where it is coupled, and where you would safely modify it.
