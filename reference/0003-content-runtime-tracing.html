Quick Reference

Tracing the Content Runtime

Use this sheet when you need to follow one behavior across multiple modules in the extension. This is no longer “syntax reading.” It is execution-graph reading.

1. Start at the entrypoint, then ask who promotes the system

defineContentScript({
  main(ctx) {
    createContentActivationController(ctx).start();
  },
});

First question: does this entrypoint do the full job itself, or does it decide when to hand off to a heavier subsystem?

2. Separate trigger code from steady-state runtime code

In this repo, contentActivation.ts is a lightweight trigger layer. contentWorker.ts and conversionRuntime.ts are the steady-state runtime layer.

Reading rule: if one file scans, debounces, or lazy-loads, and another hydrates, observes, and updates state continuously, they have different responsibilities.

3. Lazy promotion is an architectural move

setContentWorkerStartupOptions(options);
await import(getExtensionResourceUrl("content-worker.js"));

Read this as “do not pay the full runtime cost until the page shows evidence that the feature is needed.”

4. Mutation observers usually need a batching seam

const mutationObserver = new MutationObserver((mutations) => {
  mutationBatcher.push(mutations);
});

Raw DOM mutation streams are noisy. A batcher is often the seam between observation and meaningful work.

5. Runtime objects often hide a small state machine

return {
  initialize,
  onSettingsStorageUpdate,
  enqueueMutationRoots,
  recordSelectionConversion,
  shouldIgnoreMutations,
  cleanup,
};

If a factory returns a bundle of methods over closed-over state, treat it like a local service with lifecycle phases, not just “a bunch of functions.”

6. Crossing package boundaries usually means “stable seam”

import { createInlineRuntime } from "@fx-inline/inline-runtime/extension";

When the app layer imports a package entrypoint instead of deep internals, that is a clue that the package is the intended abstraction boundary.
